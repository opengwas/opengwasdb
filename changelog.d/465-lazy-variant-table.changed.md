- **A query a search index can answer no longer opens a 0.2.x Store Release's Variant Table or `index.sqlite`, and `open_store` no longer imports `pysam` or `sqlite3` (issue #465, epic #450).** The tabix handle and the `variant_aliases` connection open on first use, and an ALID or rsID found in the mmap'd search indexes resolves to its row without a table read. Only a long ALID (over 32 bytes), `range_phewas`, `variants_table()`, resolved rows with variant info, and an rsID missing from the rsID index still open them; a Hybrid release resolves identifiers once, against its shared index, so an off-panel indexed rsID no longer consults the Dense Component's `variant_aliases`. After `close()` the table raises instead of reopening. Answers are unchanged (every fixture digest is the same). Measured per process on OGS-00009 (7 fresh processes each, medians): `import pysam, sqlite3` 50 ms and opening the tabix handle 43 ms are no longer paid by a query that does not need the table (`sqlite3.connect` is 0.2 ms); a process that opens OGS-00009 and runs one 10-variant by 100-Analysis `lookup` takes 2,354 ms (2,294–2,597) against 2,423 ms (2,399–2,506) before, so the saving is of the order of the 90 ms above and inside run-to-run noise at this size. The store-comparison harness's `random_lookup` shapes and `phewas` are unchanged (it opens a release once); `benchmarks/benchmark_process_start.py` measures the per-process cost.
  On Ragged and Hybrid releases, `lookup` by a multi-allelic rsID now returns every row it names, as on Dense, where it returned only the lowest.
